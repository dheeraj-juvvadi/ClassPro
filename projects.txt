#1  REXY — LOCAL-FIRST ON-DEVICE AI MEMORY SYSTEM FOR ANDROID
================================================================================

1. ONE-LINE PITCH
-----------------
Rexy indexes everything on your Android phone (photos, documents, SMS, contacts,
files), builds a local searchable database, and lets you ask natural-language
questions that are answered by a large language model running entirely
on-device — no cloud, no data leaving the phone.

2. WHY IT EXISTS
----------------
- Every "AI assistant" on a phone ships your private data (messages, photos,
  documents) to a remote server to do retrieval-augmented generation.
- Rexy's thesis: privacy is an architecture decision, not a policy. If the
  index and the model both live on the device, no data can leak by design.
- Secondary motivation: offline capability. Cloud assistants are useless with
  no signal; a local index + local model still answers.
- Technical motivation: proving that a usable RAG pipeline fits inside a phone
  — constrained RAM, no CUDA, a shared NPU/GPU, and thermal limits.

3. WHAT IT IS / SCOPE — HONEST BOUNDARY
---------------------------------------
- Status: an ACTIVE PROTOTYPE (the repo README says this explicitly). It is not
  a published app on the Play Store.
- Three real, working components:
    a) A Jetpack Compose Android app that does retrieval + local generation.
    b) A Python indexing pipeline that runs on a Mac and pushes the index to the
       phone over ADB.
    c) An experimental macOS companion app (SwiftUI/Xcode) for managing device
       indexing from a desktop UI.
- The app runs even without the big model files, but then it falls back to a
  hash-based stub embedder (search accuracy becomes effectively random). Real
  retrieval requires the ONNX embedding model; real generation requires the
  .gguf LLM.
- Generated artifacts (indexes, phone extracts, APKs, native build folders,
  virtualenvs, model weights) are intentionally NOT committed.

5. ARCHITECTURE — COMPONENTS AND DATA FLOW
------------------------------------------
On-device object graph (created once in RexyApplication as singletons):

  RexyApplication
   ├── ModelManager        -> owns the llama.cpp JNI lifecycle
   ├── IndexRepository     -> opens SQLite index.db (ADB-pushed from Mac)
   ├── EmbeddingEngine     -> MiniLM-L6-v2 ONNX, 384-d, on-device
   ├── HybridSearchEngine  -> sqlite-vec vector search + FTS5 BM25, fused
   └── ChatDatabase (Room) -> chat history persistence

  UI (Jetpack Compose)
   ├── HomeScreen    -> memory grid + category chips
   ├── ChatScreen    -> streaming chat + SiriOrb animation
   ├── SearchScreen  -> real-time hybrid search + result cards
   └── SettingsScreen-> model status, index stats, inference tuning

Two-phase offline/online data flow (this is the clever part):

  PHASE A — INDEX BUILD (on a Mac, not the phone; the phone is too weak to
            embed a whole device's content quickly):

    Android Phone  ──ADB──▶  M1 Mac  ──ADB──▶  Android Phone
     (raw files)              (OCR + embed)     (index.db + model files)

  PHASE B — RUNTIME QUERY (100% on the phone, no network):

    user question
      -> EmbeddingEngine embeds the query (MiniLM ONNX)
      -> HybridSearchEngine runs vector search + BM25 in parallel
      -> Reciprocal-Rank / weighted fusion
      -> top-K chunks fetched from index.db
      -> PromptBuilder assembles a ChatML prompt with the chunks as context
      -> ModelManager runs llama.cpp to stream an answer
      -> answer + source cards rendered in Compose

  PHASE C — OPTIONAL WEB CONTEXT: WebContextFetcher can add web text to the
            prompt when the user explicitly wants it; PromptBuilder takes a
            `webContext` parameter and surfaces it in [APP STATUS].

6. HOW IT ACTUALLY WORKS — IMPLEMENTATION DETAIL
------------------------------------------------

6.1 INDEX SCHEMA (index_builder.py, _create_schema / _create_vec_table)
The index is a single SQLite file. Pragmas set for speed/safety balance:

    PRAGMA journal_mode = WAL;          -- write-ahead logging
    PRAGMA synchronous  = NORMAL;       -- durability/perf tradeoff
    PRAGMA cache_size   = -32000;       -- 32 MB page cache (negative = KiB)
    PRAGMA temp_store   = MEMORY;

Three data structures live in one file:

  (a) chunks — the canonical row store:
        id, chunk_id (UNIQUE, "{source_path}::chunk_{n}"), text,
        source_type, source_path, chunk_index, total_chunks,
        timestamp, metadata (JSON string)
      Plus indexes on source_type and source_path.

  (b) chunks_fts — keyword search (this is the BM25 half):
        CREATE VIRTUAL TABLE chunks_fts USING fts5(
            text, chunk_id UNINDEXED, tokenize = 'porter unicode61');
      'porter unicode61' = Porter stemming + Unicode-aware tokenisation,
      which matters because the corpus is mixed-language (English + Hinglish
      SMS, filenames, OCR noise).

  (c) vec_chunks — the vector half (sqlite-vec extension):
        CREATE VIRTUAL TABLE vec_chunks USING vec0(embedding FLOAT[384]);
      384 = all-MiniLM-L6-v2's output dimension.

  (d) rexy_meta — key/value table recording how/when the index was built.

  Why one SQLite file matters: it is a single artifact that can be atomically
  pushed over ADB and read on-device with no server, no daemon, no index
  rebuild, and no partial-state corruption.

6.2 CHUNKING (chunker.py) — constants and the tricky part
    CHUNK_TOKENS   = 512     target chunk size
    OVERLAP_TOKENS = 50      overlap between adjacent chunks
    TOKENS_PER_WORD = 1.35   wordpiece expansion factor (word -> token estimate)

  The strategy: split on sentence boundaries FIRST, then pack sentences into
  ~512-token windows with 50 tokens of overlap. Token count is approximated as
  len(text.split()) * 1.35 — deliberately avoiding a tokenizer dependency.

  The subtle engineering is in _split_sentences(): naive regex sentence
  splitting destroys abbreviations and decimals. So it first REPLACES risky
  dots with a placeholder, then splits, then restores:
      "Mr|Mrs|Ms|Dr|Prof|Sr|Jr|vs|etc|Inc|Ltd|Corp|Co." -> \1<DOT>
      "3.14"                                           -> 3<DOT>14
    then: re.split(r"(?<=[.!?])\s+(?=[A-Z\d\"])", text)
    then: restore <DOT>, and additionally split on blank-line paragraph breaks.

  Why overlap matters: a fact that straddles a chunk boundary must still be
  retrievable. 50 tokens of overlap is the cheap insurance.

  TextChunk is a dataclass carrying: chunk_id, text, source_path, source_type,
  chunk_index, total_chunks, approx_tokens, metadata.

6.3 EMBEDDINGS (embedder.py)
    MODEL_NAME      = "sentence-transformers/all-MiniLM-L6-v2"
    EMBEDDING_DIM   = 384
    DEFAULT_BATCH_SIZE = 64

  Device selection is a strict priority ladder — MPS beats CUDA beats CPU:
      _select_device(): torch.backends.mps.is_available() -> "mps" ... -> "cpu"
  The model is LAZY-loaded on first use, and there is an explicit warm-up
  encode of ["warmup"] so the first real batch is not pathologically slow.

  Measured/planned throughput on an M1 Pro (documented in the file header):
      model ~90 MB; MPS throughput ~2,000-4,000 tokens/s
      10,000 chunks x ~300 tokens avg -> ~3-8 minutes

6.4 ON-DEVICE EMBEDDING (EmbeddingEngine.kt)
  This is where the project stops being a Python script and becomes real
  on-device inference engineering:

    EMBEDDING_DIM = 384, MAX_SEQ_LEN = 128
    Tokenizer: WordPiece with [CLS] [SEP] [PAD] [UNK]

    Session options (the interesting part):
      addNnapi()                                   -- Qualcomm Hexagon NPU first
      addXnnpack(intra_op_num_threads = 4)         -- ARM NEON fallback
      setIntraOpNumThreads(4)
      setOptimizationLevel(ALL_OPT)

  That provider ladder — NNAPI, then XNNPACK, then default CPU — is the
  standard way to get acceptable latency for a transformer on ARM. Output is
  384-d float32, L2-normalized so cosine similarity becomes a dot product.
  The vocab is loaded from vocab.txt into a String->Int map; the model and
  vocab are pushed to the app's external-files dir alongside index.db.

6.5 HYBRID RETRIEVAL — THE CORE ALGORITHM (HybridSearchEngine.kt)
  Constants you should be able to defend out loud:

      private val alpha: Float = 0.7f      // vector weight
      const val DEFAULT_TOP_K   = 5        // final results returned
      const val CANDIDATE_POOL  = 20       // candidates pulled per retriever

  The search() function is a coroutine and runs the two retrievers
  CONCURRENTLY, timing each:

      val vectorDeferred = async { index.vectorSearch(queryEmbedding, CANDIDATE_POOL) }
      val ftsDeferred    = async { index.ftsSearch(query, CANDIDATE_POOL) }

  Then it fuses:
      allChunkIds = vectorResults.keys UNION ftsResults.keys
      for each id:
          vecScore = vectorMap[id] ?: 0f
          ftsScore = ftsMap[id]    ?: 0f
          hybrid   = alpha * vecScore + (1f - alpha) * ftsScore   // 0.7/0.3
      sort desc by hybrid, take topK * 3      // OVER-FETCH before filtering

  Then it fetches full chunk rows from SQLite, re-attaches the three scores
  (hybridScore, vectorScore, ftsScore), applies an optional content-type
  filter, and finally takes topK.

  Design reasoning worth stating in an interview:
   - Why hybrid at all: pure embeddings miss exact strings — a phone number,
     an account number, a filename, an error code. BM25 nails those; embeddings
     miss them because they are semantically arbitrary. Pure BM25 misses
     paraphrase ("money" vs "payment"). You need both.
   - Why alpha = 0.7: semantic intent should dominate for natural-language
     questions, but keyword signal must still be able to promote exact matches.
   - Why over-fetch topK*3: the content-type filter is applied AFTER fusion,
     so the pool must be wider than the answer set or filtering would starve
     the result list.
   - Why the scores are kept separately and returned: it makes retrieval
     debuggable. You can see WHY a chunk won — vector or keyword.
   - Timing instrumentation: embedMs, vectorMs, ftsMs, totalMs are returned in
     RetrievalResult and logged. Retrieval latency is treated as a first-class
     metric, not an afterthought.

6.6 INTENT ROUTING (HybridSearchEngine.parseIntent)
  Before retrieval, queries are pattern-matched to narrow the search space.
  This is a cheap, deterministic pre-filter — the pragmatic alternative to
  running an LLM classifier on-device.

    ParsedIntent(cleanQuery, contentTypeFilter, targetApp, temporalFilter)

    Rule 1 — "search X on WhatsApp" / "find X in Gmail"
      Regex: (?:search|find|look for)\s+(.+?)\s+(?:on|in)\s+(\w+)
      App -> type mapping:
        whatsapp|telegram|sms -> SearchResult.TYPE_MESSAGE
        gmail|mail            -> SearchResult.TYPE_EMAIL
        drive|docs|dropbox    -> SearchResult.TYPE_DOCUMENT
        photo|gallery|camera  -> SearchResult.TYPE_PHOTO
      The extracted search term becomes cleanQuery; the type becomes the
      contentTypeFilter passed into search().

    Rule 2 — "photos of X" / "pictures of X" / "images of X"
      Strips several prefix variants ("show me photos of ", "find photos of ")
      and forces TYPE_PHOTO.

    TemporalFilter enum exists: TODAY, LAST_WEEK, LAST_MONTH, LAST_YEAR.

  Interview framing: this is a two-stage router — a fast deterministic stage
  handles the common, enumerable intents, and everything else falls through to
  semantic hybrid retrieval. It is a good example of NOT using an LLM where a
  regex is cheaper, faster, and more predictable.

6.7 PROMPT ASSEMBLY — THE RAG PROMPT (PromptBuilder.kt)
  This is the file that turns retrieval into an answer. It is an object with a
  single build() function producing a ChatML-style prompt.

    Constants:
      IM_START = "<|im_start|>"   IM_END = "<|im_end|>"
      roles: system / user / assistant
      MAX_CONTEXT_TOKENS     = 420     // budget for retrieved context
      APPROX_CHARS_PER_TOKEN = 4       // cheap token estimation

    build(query, history, retrievedChunks, indexStats, webContext, memories,
          deviceOwnerName, currentDate)

    Prompt layout, in order:
      1. <|im_start|>system   -> Rexy persona
      2. <|im_start|>user     -> [APP STATUS] ... [END]   (index/web state)
      3. <|im_start|>user     -> [USER MEMORY]  ... [END] (last 8 memories)
      4. <|im_start|>user     -> [DEVICE CONTEXT] ... [END]
                                 the retrieved chunks, but only TAKE(2),
                                 each rendered as
                                 "N. <title (<=80 chars)> (<contentType>, <appName|device>)"
      5. recent conversation history (last N turns)
      6. the user's new message as the final human turn

    Why this matters for an interview:
      - [DEVICE CONTEXT] is the RAG grounding section. Everything the model is
        allowed to "know" about the user's phone arrives here.
      - retrievedChunks.take(2) is a deliberate context-budget decision: a 3B
        Q4 model on a phone has a tiny usable context, so dumping top-5 chunks
        would crowd out the conversation and degrade instruction-following.
      - The explicit section markers ([APP STATUS], [USER MEMORY],
        [DEVICE CONTEXT], [END]) give the model unambiguous boundaries so it can
        distinguish retrieved facts from user claims and from its own persona.
      - memories.takeLast(8) bounds personalisation the same way.
      - MAX_CONTEXT_TOKENS = 420 with a 4-chars-per-token estimate keeps the
        context block within budget without shipping a real tokenizer to the UI.

6.8 LOCAL LLM INFERENCE (rexy_llama_jni.cpp + ModelManager.kt)
  The generation half is llama.cpp bound to Kotlin through a hand-written JNI
  bridge. Key implementation facts from the C++:

    struct RexyContext {
        llama_model*   model;
        llama_context* ctx;
        int n_ctx   = 4096;    // context window
        int n_batch = 128;     // prompt batch size
        std::mutex mutex;      // one inference at a time per context
    };

    - Backend init is guarded by std::call_once(g_backend_once, ...) calling
      llama_backend_init() — correct, thread-safe one-time global init.
    - A llama_sampler chain is built explicitly, in this order:
        top_k(32)  ->  top_p(top_p)  ->  temp(temperature)  ->  dist(seed)
      This is the modern llama.cpp sampling API; the ordering matters because
      each sampler transforms the candidate distribution for the next.
    - tokenize() wraps llama_tokenize with a two-pass null-buffer call to size
      the token vector, and throws on INT32_MIN (the overflow sentinel).
    - Strings cross the boundary through jstring_to_string(), which correctly
      calls ReleaseStringUTFChars — a classic JNI leak source handled properly.
    - A per-context std::mutex serialises generation, which is the right call
      on a phone where concurrent decode would thrash memory bandwidth.

  Kotlin side: ModelManager owns lifecycle (load/close), LlamaInference streams
  tokens, SettingsScreen exposes inference tuning, ChatScreen renders the
  stream with the SiriOrb animation.

7. MEASURED NUMBERS
-------------------
  (Only what is actually stated in the repo — do not inflate these.)

  - Embedding model: all-MiniLM-L6-v2, ~90 MB, 384 dimensions.
  - MPS throughput planning figure: ~2,000-4,000 tokens/s on M1 Pro.
  - 10,000 chunks x ~300 tokens avg -> ~3-8 minutes to embed.
  - Batch size 64 for indexing; MAX_SEQ_LEN 128 on-device.
  - LLM: Llama-3.2-3B-Instruct, Q4_K_M quantisation, ~2 GB on disk.
  - On-device context window: n_ctx = 4096; prompt batch n_batch = 128.
  - Retrieval: top-K = 5 final results from a 20-candidate pool per retriever,
    fused with alpha = 0.7 vector / 0.3 keyword.
  - Context injected into the prompt: top 2 retrieved chunks, ~420-token
    budget, ~4 chars/token.
  - Hardware target: Snapdragon 8 Gen 1+, Android 12+, 12 GB+ RAM.

  What is NOT measured and must not be claimed: no retrieval quality metric
  (no recall@k / MRR / nDCG benchmark), no tokens/sec figure for the on-device
  GGUF model, and no accuracy comparison against a cloud baseline. Those are
  the obvious next measurements — and saying so is a strength, not a weakness.

8. INTERVIEW TALKING POINTS
---------------------------
- "I built the full RAG loop, not a wrapper: chunking -> embedding -> hybrid
  retrieval -> prompt budget -> local generation -> streaming UI."
- The hybrid-retrieval decision is the best story: explain why pure vectors
  fail on exact identifiers (phone numbers, filenames) and why pure BM25 fails
  on paraphrase, then show the 0.7/0.3 fusion with per-retriever scores
  retained for debuggability.
- Explain the two-phase architecture as a resource decision: the phone cannot
  afford to embed a whole device, so indexing is offloaded to an M1 Mac and
  only the finished index travels back over ADB. That is a real systems
  tradeoff, not a shortcut.
- On-device inference depth: NNAPI -> XNNPACK -> CPU provider ladder, 4
  intra-op threads, ALL_OPT, lazy model load with a warm-up pass, L2-normalized
  embeddings, and a mutex-guarded llama.cpp context.
- Prompt engineering under a hard budget: sectioned prompt with explicit
  [DEVICE CONTEXT] grounding, only top-2 chunks, last-8 memories, 420-token
  context cap — every number is a deliberate constraint, not a default.
- Deterministic routing before LLM routing: regex intent parsing for
  "photos of X" / "search X on WhatsApp" because it is faster and predictable.

9. HONEST LIMITATIONS
---------------------
- It is an active prototype, not a shipped/published product.
- No retrieval-quality evaluation exists yet (no recall@k / MRR / nDCG). If
  asked "how do you know retrieval works?", the honest answer is: "I
  instrumented latency and per-retriever scores, but I have not yet built a
  labelled retrieval benchmark — that is the next thing I would do."
- Without the ONNX model pushed, the app silently falls back to a hash-based
  stub embedder; search accuracy is then effectively random. This is disclosed
  in the README, which is good practice but also a sharp edge.
- The prompt builder's composition uses ChatML (<|im_start|>), which is the
  Qwen2.5 convention, while the documented model is Llama-3.2-Instruct (which
  uses its own header tokens). That is an inconsistency worth flagging
  proactively — it is exactly the kind of detail an interviewer respects you
  for catching yourself.
- The on-device WordPiece tokenizer is explicitly described as simplified
  ("for full accuracy, replace with a proper HuggingFace tokenizer"), so
  embedding quality on-device is below the indexing-side quality.
- No published tokens/sec, thermals, or battery measurements on a physical
  phone.

#2  ANON (revamp-tracker) — PRODUCTION STUDENT-PORTAL AI COMPANION
================================================================================

1. ONE-LINE PITCH
-----------------
Anon is a production web app that logs into SRM Institute's student portal on
the user's behalf — including reading the CAPTCHA with a locally-run CRNN
neural network — and turns a slow, session-expiring portal into a fast,
cached, offline-capable companion for attendance, marks, CGPA and timetable.

2. WHY IT EXISTS
----------------
- SRM's official Student Portal is slow, throws sessions away constantly, and
  requires re-solving a CAPTCHA on every visit. Students check attendance and
  marks several times a week and pay that cost every time.
- Nobody wants to type a password into a random third-party site. So a core
  design goal was: credentials are never persisted, portal cookies never leave
  the server, and the browser only ever holds an opaque random session id.
- The CAPTCHA is the hard technical bottleneck. Solving it by hand on a phone
  is the single worst part of the experience, and it is the reason a real
  trained model (rather than a scraper) had to exist.
- Secondary goal: make the data useful — projections, date planning, reminders,
  grade targets — rather than just mirroring the portal's tables.

3. WHAT IT IS / SCOPE — HONEST BOUNDARY
---------------------------------------
- This is REAL and DEPLOYED. Production frontend: https://anon-tracker.vercel.app
  Deployment repository: dheeraj-juvvadi/revamp-tracker, branch main, Vercel root
  directory portal-app/public. The Python backend runs on an Azure VM.
- It has real users, real uptime concerns, a real incident postmortem, and a
  private ops dashboard for the owner.
- The upstream client is AGPL-3.0 licensed and is used as a pinned dependency
  (`413b7f0055a14794ea11cb858c05abab311f89b4`). Some files under
  portal-python/core and portal-python/services are copied from it unchanged,
  with the license retained. This is correctly attributed, not hidden.
- Honest scope note: reliability of the automatic CAPTCHA login is a milestone,

6. HOW IT ACTUALLY WORKS — IMPLEMENTATION DETAIL

6.1 THE CAPTCHA OCR MODEL — the genuine ML component
  File: portal-python/ocr.py  (58 lines) + portal-python/model/

  What it is: a CRNN (convolutional recurrent neural network) trained for
  CAPTCHA recognition, exported to ONNX, executed locally with ONNX Runtime on
  CPU. It is NOT a third-party OCR API. Images never leave the server.

  Provenance (this is the part that shows rigour):
    Source: https://github.com/wtfPrethiv/TinyOCR
    Revision: d59c4474cb5371bbe7866b18e6ffa1af0908dbae (2026-08-23)
    License: MIT (retained in portal-python/model/LICENSE)
    captcha_crnn.onnx generated from upstream best_captcha_crnn.pt using the
    upstream's UNCHANGED scripts/export_onnx.py
    Checkpoint SHA256: e9072bf58ad9ccbba4326ae9f2a607e6d64edebd52cd9ac0025e21aea419326e
    ONNX SHA256:       339c366ccd8356a9707157b3ebd789d2d4f2e430a07db23c6091d7ea4a6636ff
    Export env: Python 3.11, torch 2.6.0, onnx 1.17.0, onnxruntime 1.22.1,
                numpy 2.2.6, Pillow 11.3.0

  Export PARITY GATE (the important verification step):
    Predictions matched PyTorch for ALL 512 bundled test images, plus random
    batches of size 1/2/8/16. Maximum real-image logit difference: 3.815e-05.
    Accuracy against bundled filenames: 494/512.
    The docs explicitly caveat that this is not a production login-acceptance
    measurement — correct, and worth repeating in an interview.

  The inference path in ocr.py, step by step:
    1. _load_session(root) — double-checked locking (module-level _session plus
       a threading.Lock) so the ONNX session is created exactly once even under
       concurrent logins.
       SessionOptions: intra_op_num_threads = 1, inter_op_num_threads = 1,
       log_severity_level = 3, providers = ["CPUExecutionProvider"].
       -> ONE thread is deliberate: the service runs many OCR requests across
          workers, so per-request parallelism would oversubscribe the CPU.
    2. _charset(root) — lru_cache(maxsize=2) over vocab.json. It validates
       vocabulary["blank_idx"] == 0 and raises if not, because the greedy CTC
       decoder below hard-codes blank index 0. Charset = " " + vocab.
    3. Preprocessing — EXACTLY the upstream pipeline, no resizing:
         - reject anything that is not exactly 175x45 (raise ValueError)
         - PIL convert("L") to grayscale
         - normalize: (pixel / 255.0 - 0.5) / 0.5     -> [-1, 1] range
         - reshape to [1, 1, H, W] NCHW float32
    4. logits = session.run(...)[0]
       Validate logits.shape[-1] == len(charset) or raise.
    5. Greedy CTC decoding (no beam search — chosen for latency):
         indices = argmax over the class axis per timestep
         for each index:  skip if index == 0 (blank)
                          skip if index == previous (collapse repeats)
                          else append charset[index]
       This is textbook CTC: collapse repeats first, then remove blanks.
    6. Sanity guard on the decoded string:
         must be 4..8 characters, must be ASCII, must be alphanumeric
         otherwise raise ValueError("Uncertain OCR result")
       -> This turns "the model produced garbage" into an explicit, typed
          failure the caller can retry, instead of submitting a wrong answer
          and burning a login attempt.

  Where it runs: the Go API starts ONE bounded Python process per active
  Student Portal session. The process keeps the upstream HTTPX client, cookie
  jar, CAPTCHA page and nonce in VOLATILE memory, exits on logout/expiration/
  error/restart, and has NO public listener — it communicates only over private
  stdin/stdout pipes.

  Deliberate difference from upstream: upstream calls a separate Rust TinyOCR
  service over HTTP. This adapter runs the exact same TinyOCR weights locally
  through ONNX Runtime with one CPU thread, so no third-party service ever
  receives an image.

  Retry policy (also a design decision worth explaining):
    - At most FOUR automatic attempts, and only for CAPTCHA rejection detected
      in alert elements.
    - A fresh PortalSession / cookie jar on refresh and between automatic
      CAPTCHA retries.
    - Credentials rejection or unknown failure STOPS submission — it does not
      request another CAPTCHA. (Retrying bad credentials is what gets accounts
      locked.)
    - Manual CAPTCHA entry remains available as a fallback.
    - A 2-second pre-submit delay and 90 ms portal typing timing are preserved
      because removing them empirically caused failed phone logins.
    - Prepared challenges older than 60 seconds are refreshed.

  Honest nuance the docs make explicit: the upstream classifier labels even an
  unsubmitted login page "wrong_captcha" because validation scripts contain
  that phrase. So Anon added a separate `alert_classification` diagnostic that
  inspects only alert elements (no scripts, no hidden validation messages),
  emits only fixed categories, and never page text. The adapter overrides the
  raw classifier for retry decisions and keeps the original as `upstream_reason`
  for comparison. That is careful, evidence-driven debugging.

6.5 CONCURRENCY, CAPACITY AND ADMISSION CONTROL
  This is the systems-engineering half of Anon and it is unusually rigorous.
  Live Azure settings at the time of writing:
      SESSION_LIMIT   = 200     (admission ceiling, NOT a throughput claim)
      API_CONCURRENCY = 4
      OCR_CONCURRENCY = 2
      IO_THREADS      = 8
      persistence     = 7 days
      VM: Standard_B2ats_v2, ~893 MiB RAM; idle new container ~90 MiB

  Request classes and their limits (docs/azure-capacity.md):
    - Login / mutation handlers: EIGHT workers, FIFO overflow queue, bounded.
    - Refresh: FOUR background workers, at most one job per session,
      2,000 queued maximum. REFRESH_QUEUE_WAIT = 600 seconds (queued work
      expires after ten minutes).
    - A started upstream refresh has its own 90-second limit.
    - Light queues return a 200-299 ms follow-up hint so the client polls
      sensibly instead of hammering.

  Memory admission (capacity.py):
    - Expensive work and new sessions PAUSE below 160 MiB available memory.
    - The check is done on BOTH available memory and a memory permit that is
      released before waiting, so a burst cannot deadlock itself.
    - Removed/expired sessions are checked BEFORE contacting upstream.
    - Removed sessions release their queue slot and go straight back to login.

  Session store optimisation (session_store.py) — a real measured win:
    Problem: every save re-serialized and RE-ENCRYPTED the whole payload even
    when nothing had changed.
    Fix: detect unchanged payloads and skip re-encryption; update only the
    expiry field separately.
    Result (synthetic, network-disabled container, 0.5 CPU / 256 MiB,
    112 sessions x 30 save/restore cycles):
        before: median 552.47 ms, p95 601.95 ms, peak RSS 44,820 KiB
        after:  median  99.59 ms, p95 100.73 ms, peak RSS 44,680 KiB
    -> roughly a 5.5x latency reduction, and it was shipped as an image
       (classpro-diag:20260917-store) after 47 tests passed.

  Per-session request locks, cancellation-safe OCR permits (a native OCR
  inference RETAINS its slot after request cancellation until inference
  actually exits — otherwise a cancel would free a slot that is still burning
  CPU), configurable rate limits (default 30/IP/min with separate 30/min
  buckets for issued sessions AND unfinished sign-ins), and module-scoped
  upstream print suppression (no process-wide stdout redirection).

6.6 SECURITY MODEL (worth being able to recite)
    - Session cookie: Secure, HttpOnly, SameSite=Strict, host-only.
    - Cookies contain only opaque random session identifiers — no upstream
      state is ever serialized into them.
    - Mutations require exact Origin, a session CSRF token, and (for ops)
      password confirmation.
    - Login attempts have persistent per-source AND global limits.
    - In-memory sessions expire after 30 idle minutes; remembered (disk)
      sessions after 7 days of inactivity; unchecked "Keep me signed in" uses a
      browser-session cookie with a 30-minute idle timeout and NO disk write.
    - Credentials are never persisted. Passwords are request-local.
    - Session store encryption with Fernet; the key and encrypted SQLite
      records must survive container replacement and are restricted to the
      container user (SESSION_STORE_DIR points at the mounted persistent dir).
    - Diagnostics contain only fixed classifications, status codes, attempt
      numbers, stages and exception class names — never page text.
    - The ops bridge: Vercel signs requests to a loopback Azure agent with
      HMAC-SHA256 plus timestamps and one-time NONCES (replay protection).
      A secret gateway header filters requests at the proxy. Bridge secrets live
      in production env vars and a root-readable host file, never in frontend
      assets. The owner password is stored only as a SALTED SCRYPT HASH on
      Azure. Deployment webhook signatures are verified before events are
      accepted.
    - The ops agent runs as its own user with a 100 MB memory cap, 10% of one
      CPU, low scheduling priority, eight HTTP workers, bounded requests, and a
      narrow sudo allowlist. Its root-owned helper accepts only THREE fixed
      operations — it CANNOT execute arbitrary commands from the dashboard.
    - Client logs bounded to 2 MB/day, 120 events/minute, 7 days retention.
      Analytics keeps at most 10,000 events and 7 days; host samples 7 days;
      audits 30 days. Presence saves aggregate expiry buckets — never user IDs
      or session tokens — at most once every five seconds.

6.7 THE PRODUCTION INCIDENT (docs/postmortem.md) — a strong interview story
    Date: September 19-20, 2026. Duration: ~7 hours of degradation.

    Symptom: the Azure VM went to ~95% CPU with ~477 GB of DISK READS per hour,
    while actual network traffic was tiny (~3.5 MB in, 2.4 MB out).

    The key analytical move: they proved it was NOT an attack. The huge numbers
    were reads from the server's own disk, not visitors downloading hundreds of
    gigabytes. When memory is exhausted the OS thrashes — reading the same 1 GB
    a hundred times counts as 100 GB of reads even though the information is
    1 GB. The VM had only 892 MiB of usable RAM.

    Suspected trigger: a scheduled firmware-information refresh that started
    immediately before the spike; later logs explicitly reported memory
    pressure. Extra guest monitoring services were also consuming memory.
    Stated honestly: "the exact offending process was not captured because
    normal logging also stalled" — this was never claimed as a proven bug.

    The second, confirmed failure: restarting cleared the resource spike but
    changed the server's temporary Cloudflare tunnel address. The website kept
    calling the OLD address. The backend was healthy but unreachable. This was
    confirmed directly, and is a classic example of a restart-induced
    configuration regression.

    Fixes shipped:
      - Permanent HTTPS Azure hostname replacing the temporary tunnel; the old
        tunnel was disabled; HTTPS auto-starts and handles cert renewal.
      - Disabled the suspected firmware refresh and blocked its services from
        restarting (normal OS security updates left on).
      - Freed memory: removed the guest monitoring agent. Available RAM went
        from ~164 MiB to ~329 MiB.
      - Contained runaway memory: capped the app at 384 MiB, retained low-memory
        admission checks, added HTTPS limits. The deployment script carries the
        limits forward. A runaway app may restart at its limit but can no longer
        consume the whole VM.
      - No VM size upgrade; saved user sessions preserved.

    Follow-up: the private ops dashboard (anon-ops) was built after this, with
    a deliberately small footprint — 100 MB ceiling, limited CPU, one-minute
    samples, and it reads only NEW log bytes (256 KB per collection) instead of
    rescanning old files. Recovery actions require a password and have cooldowns
    and a three-attempt daily limit; automatic recovery starts OFF.

    Why this matters in an interview: it demonstrates hypothesis-driven
    incident analysis under uncertainty, the discipline to separate "what I
    proved" from "what I suspect", and the judgement to fix the blast radius
    (caps and admission control) rather than just the symptom.

8. INTERVIEW TALKING POINTS
---------------------------
- "The most interesting ML in my production system is a CRNN that reads
  CAPTCHAs entirely on my own server — I never send a user's document or image
  to a third-party OCR API."
- Walk the export-parity gate: I verified my ONNX export matched PyTorch on
  512 images with a max logit difference of 3.8e-05, pinned both SHA256 hashes,
  and locked the preprocessing to the upstream's exact 175x45 grayscale with
  [-1,1] normalization — because changing any of those silently breaks a model.
- Greedy CTC decoding with a sanity guard: collapse repeats, drop blanks, then
  REJECT any decode that is not 4-8 ASCII alphanumerics. That guard converts
  garbage output into a typed, retryable failure instead of a wrong CAPTCHA
  submission that burns a login attempt.
- Retry policy as a safety decision: retry ONLY explicit CAPTCHA rejections,
  cap at four attempts, fresh cookie jar between retries, and never retry bad
  credentials — because retrying credentials is what locks accounts.
- The memory-pressure admission design: work pauses below 160 MiB available,
  and the memory permit is released before waiting, so a burst cannot deadlock.
- The session-store change is a great "small fix, big win" story: skipping
  re-encryption of unchanged payloads cut median save latency from 552 ms to
  100 ms.
- The incident postmortem: prove it isn't an attack by comparing network bytes
  against disk reads, explain OS thrashing in plain language, then find the real
  second bug (the restart changed the tunnel hostname, so the frontend was
  calling a dead address). Then fix the blast radius with memory caps and
  admission control.
- I can talk about what I refused to claim: the repo repeatedly separates
  measured capacity from real-world SRM throughput, and states that one
  successful automatic login is a milestone, not a reliability benchmark.

9. HONEST LIMITATIONS
---------------------
- Real multi-user login capacity was never measured against the live SRM
  portal. Synthetic burst and OCR benchmarks are explicitly not that.
- The 200-session limit is an ADMISSION CEILING, not measured simultaneous
  login capacity or resource headroom.
- The OCR confidence thresholds mentioned in the earlier Node adapter
  (mean >= 90, min char >= 80 on a 0-100 scale; Tesseract fallback requiring
  two agreeing variants and mean >= 65) are stated in the docs as UNCALIBRATED,
  and model scores are not measured accuracy.
- Earlier backend attempts where the user typed the CAPTCHA failed; the first
  success changed browser configuration AND OCR at the same time, so the
  successful result does not isolate each change's causal contribution. The
  docs say this outright.
- The VM is genuinely small (~893 MiB usable RAM) with no size upgrade, so the
  architecture is bounded by design rather than by choice.
- Legacy code paths remain: portal-app/src/server.js (historical Node backend),
  appwrite-backend/, supabase/. These are retained but are NOT production, and
  the backlog explicitly tracks the unresolved decision of whether to retire
  them.
- Some items are still open in implementation-backlog.md: physical-phone motion/
  scroll/battery verification, controlled real SRM burst measurement, and an
  automated review of production client-error summaries.

#3  SAFETY-GATED EDGE MACHINE LEARNING FOR AVIONICS ANOMALY DETECTION
================================================================================

1. ONE-LINE PITCH
-----------------
A real-time flight-telemetry anomaly detection system that runs an ensemble of
three ML models (PCA reconstruction, One-Class SVM, and a deep MLP) over
avionics sensor data, and — crucially — passes every ML decision through a
DETERMINISTIC safety gate before anything actionable reaches a cockpit.

2. WHY IT EXISTS
----------------
- Aircraft generate enormous volumes of telemetry, but the systems that watch
  it are largely threshold-based: they fire when a single parameter crosses a
  fixed limit. That misses correlated, multi-parameter drift where every
  individual value still looks normal.
- The obvious fix — "let a neural network decide" — is unacceptable in
  safety-critical aviation. A model that is right 99% of the time is still
  wrong 1% of the time, and in an aircraft an automated wrong action is worse
  than no action at all.
- That tension is the entire thesis of this project: use ML to DETECT and
  LOCALISE anomalies (where being probabilistic is fine), but never let ML
  AUTHORISE a mitigation action. Authorisation stays deterministic and
  auditable. The project calls this a "safety gate".
- Research framing came from a documented gap analysis: explainable AI,
  real-time processing, and rare-failure detection are the open problems in
  aircraft predictive maintenance.

5. ARCHITECTURE
---------------
Event-driven architecture: every incoming telemetry update is treated as an
independent EVENT and processed immediately, not batched. This is a deliberate
choice for safety-critical monitoring, where near-real-time reaction matters.

  telemetry event
     |
     v
  feature engineering        (normalize, denoise, derive diff + rolling stats)
     |
     v
  anomaly detection          THREE models in parallel:
     |                         - PCA reconstruction   (unsupervised baseline)
     |                         - One-Class SVM        (novelty detection)
     |                         - MLP neural network   (supervised patterns)
     v
  ensemble aggregation       (voting consensus across the three)
     |
     v
  safety gate                DETERMINISTIC rules -> APPROVED / BLOCKED / REVIEW / SAFE
     |
     +--> normal telemetry stored as routine operational data
     +--> anomaly -> alert event pushed to the dashboard with context + confidence

  Diagram chain in the formal architecture document:
  avionics sensors -> preprocessing -> edge inference -> safety-gated validation
  -> alert generation -> fail-safe handling -> logging -> maintenance analytics.

Actors: pilot, maintenance engineer, system administrator.

Data exchange contract (from the architecture document):
  - Frequency: CONTINUOUS near-real-time streaming for telemetry; alert
    generation is event-driven (only on anomaly, so no wasted communication);
    model training/evaluation is periodic scheduled BATCH work on history.
  - Datasets:
      input telemetry:   ALT, CAS (calibrated airspeed), EGT_1 (engine temp),
                         VIB_1 (vibration), PTCH (pitch), timestamp, flight
                         record index
      engineered features: derived difference metrics + rolling statistics
      inference output:  anomaly flags, anomaly scores, predicted issue
                         categories, confidence levels, per-model outputs
      safety decision:   status (APPROVED/BLOCKED/REVIEW/SAFE), recommended
                         action, justification
  - Modes of exchange: JSON over HTTP for API calls between backend and
    dashboard; WebSockets for real-time UI updates; CSV files for historical
    telemetry and for training/evaluation reproducibility.

6. HOW IT ACTUALLY WORKS

6.1 THE THREE MODELS (design, per README + PROJECT_DESIGN.md)

  (a) PCA RECONSTRUCTION — the unsupervised baseline.
      Fit PCA on normal flight data; reconstruct each new sample; the
      reconstruction error is the anomaly score. Systematic deviations from
      normal flight patterns produce large reconstruction error. Chosen because
      it is mathematically stable and interpretable, giving a reliable baseline
      for detecting global deviations from the normal flight envelope.
      Reported with Precision = TP/(TP+FP) and Recall = TP/(TP+FN).

  (b) ONE-CLASS SVM — novelty detection in high-dimensional space.
      Learns the boundary of NORMAL operations (trained on normal data only)
      and flags points outside that envelope. Excels at novel parameter
      COMBINATIONS never seen in training. Uses an RBF kernel for non-linear
      separation:

        f_hat(x) = sign( SUM_{i in SV} y_i * alpha_i * K(x_i, x) - rho )
          SV = support vectors, y_i = labels, alpha_i = Lagrange multipliers,
          K = kernel, rho = decision threshold

        K(x_i, x_j) = exp( -gamma * ||x_i - x_j||^2 )        (RBF)

      Why it complements PCA: PCA finds global magnitude deviations; a
      one-class SVM finds shape/geometry deviations in parameter space. The
      design doc frames it as learning how altitude and airspeed conditions
      define the boundary of normal flight.

  (c) MULTI-LAYER PERCEPTRON — supervised deep pattern recognition.
      Captures complex non-linear relationships between 12 engineered flight
      features. Documented architecture:

        Input (12 features) -> 128 -> 64 -> 32 -> Binary output (sigmoid)

      Reported accuracy: 99.05% on validation data. Trained on real NASA
      DASHlink data with 120 epochs and early stopping.

6.2 THE SAFETY GATE — THE ACTUAL DIFFERENTIATOR (real code)
    File: backend/core/safety_gate.py. This is the piece to lead with.
    The gate takes the raw telemetry STATE plus the ML PREDICTION and returns a
    status, an action, and a human-readable REASON.

    Control flow, exactly as implemented:

      If the ML model says there is no anomaly:
        -> status SAFE, action None,
           reason "Normal operation within flight envelope."

      If there IS an anomaly, the gate switches on the LOCALISED subsystem:

      ENGINE PERFORMANCE
        altitude < 10,000 ft:
          -> BLOCKED, "Throttle Reduction",
             reason: unsafe to reduce thrust below 10,000 ft; maintain thrust
             and alert the pilot.
        altitude >= 10,000 ft:
          -> APPROVED, "Gradual Throttle Reduction",
             reason: safe altitude; mitigating engine overheat.

      AIRSPEED SENSING
        airspeed < 200 kts:
          -> BLOCKED, "Switch to Alternate Static Source",
             reason: airspeed critically low; manual pilot verification required
             before switching sources.
        airspeed >= 200 kts:
          -> APPROVED, "Cross-check with GPS Ground Speed",
             reason: safe to cross-reference secondary sensors.

      CONTROL RESPONSE
        -> REVIEW, "Engage Backup Actuators",
           reason: control-surface anomaly requiring immediate pilot
           confirmation before engaging backup systems.

      ANY OTHER SUBSYSTEM
        -> REVIEW, "Manual Pilot Check",
           reason: anomaly detected but no automated mitigation is defined in
           the safety envelope.

    WHY THIS DESIGN IS THE POINT: the ML only ever says WHERE the problem is and
    HOW confident it is. The mapping from "problem" to "action" is pure
    deterministic rules with hard numbers (10,000 ft, 200 kts) that a human can
    audit, certify, and argue with. The default for anything unrecognised is
    REVIEW (human in the loop), never an automatic action. That is a genuinely
    correct safety architecture and it is the single best thing to talk about.

#4  MULTIMODAL TRAFFIC INCIDENT DETECTION & RESPONSE PRIORITISATION

1. ONE-LINE PITCH
-----------------
A multimodal fusion system that combines YOLOv8 vision detection, text/NLP
classification, and tabular gradient-boosted models to detect traffic
incidents, classify their severity, and score how urgently emergency services
should respond.

2. WHY IT EXISTS
----------------
- Incident detection from a single modality is brittle. Cameras see a
  collision but not that it is a fuel tanker; a text report says "multi-vehicle
  pile-up with fire" but carries no location; tabular records have severity but
  no real-time signal.
- Emergency response is a PRIORITISATION problem. When ten incidents arrive at
  once, someone must decide which gets the one available ambulance. That is a
  ranking problem, not just a classification problem.
- The project therefore fuses three streams and outputs a priority score
  (0-1), a severity class, a confidence, a response-time estimate and resource
  hints — plus similar-incident matching.

3. WHAT IT IS / SCOPE — HONEST BOUNDARY
---------------------------------------
- An academic research project ("research project bde"), associated with a
  co-authored paper accepted at IDCIoT-2026. Part of a group effort.
- It is a research/engineering pipeline with a real backend, real trained
  model artifacts, a real HDFS integration, and a real (and honestly documented)
  set of mixed results. It is not a deployed municipal system.
- IMPORTANT: this project contains BOTH genuine successes and genuine failures.
  The failures are documented in the output artifacts and are excellent
  interview material — see section 7.

CROSS-CUTTING SECTION B — PRIORITISED TOP-TEN INTERVIEW QUESTIONS + ANSWERS
================================================================================
Each answer is written as something you could actually say out loud. Keep them
short in delivery; the depth here is so you never get caught out.

Q1. "Walk me through the most technically complex thing you've built."
  A: "Rexy — an on-device RAG system for Android. The hard constraint is that
     nothing leaves the phone. So I had to solve retrieval AND generation inside
     a phone's memory budget. Range: a chunker that splits on sentence
     boundaries without breaking abbreviations, a MiniLM embedding pipeline that
     runs on an M1 Mac because the phone can't afford to embed a whole device,
     a hybrid retriever that fuses sqlite-vec vector search with SQLite FTS5
     BM25 at a 0.7/0.3 weight, and then llama.cpp bound through hand-written
     JNI with a top_k->top_p->temperature->dist sampler chain. The index is a
     single SQLite file so it can be pushed over ADB atomically."

Q2. "How do you evaluate a RAG system?"
  A: "Three layers. Retrieval: a labelled query/relevance set, reporting
     recall@k, MRR and nDCG, compared against a BM25 baseline — hybrid only
     matters if it beats pure BM25 on exact identifiers. Generation: groundedness
     and answer-correctness against the retrieved context. And operations:
     p95 retrieval latency broken down by stage. Honestly, in Rexy I
     instrumented latency and per-retriever scores but I have not yet built the
     labelled retrieval benchmark — that is the next thing I would add, and I
     have a smaller semantic-search project where the evaluation discipline was
     the point."

Q3. "Tell me about a time your model failed."
  A: "My multimodal traffic fusion model scored 0.995 on training and 0.125 on
     test — 1,000 samples, 9 features, and a model complicated enough to
     memorise the rows. I also caught a subtler mistake in the same project:
     a macro F1 of 1.0 that was meaningless because two of my four classes had
     ZERO test samples. Macro over an empty class is not a real average, and the
     artifact now records the corrected over-4-class figure of 0.5. Since then
     I always check per-class support and the confusion matrix before I quote a
     macro number."

Q4. "How do you handle a model in a safety-critical system?"
  A: "In my avionics project the ML never authorises anything. The three models
     detect and localise; a deterministic safety gate decides. If the gate
     doesn't recognise the anomaly, the default is REVIEW — human in the loop —
     never an automatic action. The thresholds are hard numbers like 10,000 ft
     and 200 kts that a human can audit and certify. That separation is the
     whole design: ML where being probabilistic is acceptable, rules where it
     isn't."

Q5. "You have a trained model. How do you ship it?"
  A: "In production I run a CRNN CAPTCHA model through ONNX Runtime on CPU with
     exactly one intra-op thread, behind a double-checked-locking singleton so
     the session is created once under concurrency. I locked the preprocessing
     to the upstream's exact 175x45 grayscale, [-1,1] normalisation, and
     greedy CTC with blank index 0 — because silently changing any of those
     breaks the model without any error message. And I built an export parity
     gate: I verified the ONNX export against PyTorch on 512 images with a
     maximum logit difference of 3.8e-05, and I pinned both the checkpoint and
     ONNX SHA256 hashes."

Q6. "How do you keep inference cheap at scale?"
  A: "I benchmarked it and then chose fewer workers than the hardware allowed.
     My CRNN ran at 323 inferences/sec with one worker and 354 with two, then
     flattened at ~356 with four and six. So I shipped two — extra workers cost
     memory and bought nothing. On-device in Rexy, the provider ladder is NNAPI
     (Qualcomm Hexagon NPU) then XNNPACK (ARM NEON) then CPU, with 4 intra-op
     threads."

Q7. "Tell me about a production incident."
  A: "My Azure VM hit 95% CPU and 477 GB of disk reads per hour while network
     traffic was only ~3.5 MB in and 2.4 MB out. The instinct was 'we're being
     attacked', but that traffic ratio proved it was the machine reading its own
     disk — classic memory thrashing on a VM with 892 MiB of RAM. Then
     restarting surfaced a second, independent bug: the temporary tunnel address
     changed, so my frontend was calling a dead hostname while the backend was
     perfectly healthy. I fixed the tunnel with a permanent hostname, removed
     the suspected firmware-refresh trigger, freed memory from ~164 to ~329 MiB,
     and capped the app at 384 MiB so no single process can take the VM down."

Q8. "Design me a system that answers questions over a private corpus."
  A: This is where you combine Rexy + Anon + Semantic Search: chunk with
     overlap at sentence boundaries; embed with a small sentence transformer;
     store vectors AND a lexical index so exact identifiers are findable;
     retrieve in parallel and fuse; budget the context explicitly; generate with
     grounding markers; then MEASURE recall@k, nDCG and p95 latency. Mention
     both the privacy architecture from Rexy and the bounded-queue admission
     control from Anon.

Q9. "What's the difference between accuracy and usefulness in ML?"
  A: "My avionics MLP hit 99.05% validation accuracy, and that number would be
     worthless on its own — because the model still doesn't get to act. The
     useful metric is whether the DETECTION plus the SAFETY GATE produces a
     decision a human can trust. In the traffic project the reverse happened:
     a 0.9857 macro AP looked great while the fused decision system was
     effectively ignoring vision. Usefulness is measured at the system level,
     not the model level."

Q10. "Why should we hire you for an applied AI role?"
  A: "Because I've built the whole path, not just the notebook. I've trained
     and exported a model that runs in production where a wrong answer costs a
     real user a login. I've built RAG end to end including on-device inference.
     I've built safety-gated ML where the model isn't allowed to act. And I've
     run the incident, written the postmortem, and capped the blast radius.
     I know where my numbers are measured and where they're assumptions, and
     I say which is which."
